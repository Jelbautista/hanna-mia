# ADR-001 — Monolito modular con Flutter + FastAPI + PostgreSQL

- **Estado**: Propuesta · **Fecha**: 2026-11-19 · **Decisores**: equipo de arquitectura (pendiente de revisión del responsable del producto)

## Contexto

MiNegocio AI necesita: (1) una app Android para gama baja que funcione sin conexión; (2) un backend
con transacciones financieras consistentes entre ventas, inventario, cobros y comprobantes;
(3) un equipo inicial pequeño; (4) poder extraer módulos más adelante (facturación, IA). El prompt
maestro fija Flutter, FastAPI, PostgreSQL, SQLite/Drift, Riverpod, SQLAlchemy 2 y Alembic; este ADR
justifica esa elección y define la forma de la arquitectura.

## Decisión

1. **Monolito modular**: un servicio API y un worker que comparten código, con 16 módulos de dominio
   y límites verificados por `import-linter`. Cada módulo expone solo `service.py` y sus eventos.
2. **App**: Flutter/Dart, Android primero, arquitectura *feature-first*, Riverpod para el estado y
   Drift sobre SQLite cifrado con SQLCipher.
3. **Backend**: Python 3.12+, FastAPI (OpenAPI automático), Pydantic v2, SQLAlchemy 2 asíncrono,
   Alembic, pytest + Hypothesis.
4. **Datos**: PostgreSQL 16+ como único motor transaccional (datos, cola de tareas y auditoría) y
   almacenamiento de objetos compatible con S3 para la evidencia.

## Alternativas consideradas

| Alternativa | Por qué no |
|---|---|
| Microservicios | Sagas para operaciones que hoy son una transacción ACID; más infraestructura y observabilidad para un equipo pequeño |
| BaaS (Firebase/Supabase) | La lógica financiera y la idempotencia de dominio quedarían en el cliente o dispersas; dependencia del proveedor; reglas tributarias difíciles de expresar |
| Kotlin nativo | Mejor rendimiento puntual, pero sin código compartido para un futuro iOS o web; Flutter rinde bien en gama baja si se cuida el presupuesto |
| React Native | Ecosistema de base de datos local cifrada y reactiva menos maduro que Drift + SQLCipher para este caso |
| Node.js / Go en backend | Viables; Python facilita la capa de IA y el procesamiento de documentos, y FastAPI da tipado + OpenAPI. El rendimiento no es el cuello de botella (I/O de BD) |

## Consecuencias

- ✅ Una transacción por caso de uso; un despliegue; depuración simple.
- ✅ El OpenAPI generado permite pruebas de contrato y clientes tipados.
- ⚠ Disciplina de límites: si se rompen, el monolito se vuelve una "bola de barro". Se mitiga con `import-linter` en CI.
- ⚠ Flutter en gama baja exige un presupuesto de rendimiento medido en CI (tamaño del APK, arranque).
- ⚠ Dos lenguajes de dominio (Dart y Python) para el cálculo de dinero: se exige el mismo conjunto de vectores de prueba (ADR-003).
